## 2. Официальный контракт POST /process (Приложение A)

Один эндпоинт обрабатывает и маскирование, и демаскирование, коррелируясь по `payload_id`:

```bash
# 1) Маскирование (новый payload_id)
curl -s -X POST http://localhost:8000/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"Клиент Иванов Иван Иванович, паспорт 4509 123456","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
# → {"result":"Клиент ⟦PII:FULL_NAME:…⟧, паспорт ⟦PII:PASSPORT:…⟧ ⟦PII:PASSPORT:…⟧"}

# 2) Демаскирование (тот же payload_id + возвращённая маска)
curl -s -X POST http://localhost:8000/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"<вставьте возвращённую маску>","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
# → {"result":"Клиент Иванов Иван Иванович, паспорт 4509 123456"}
```

Маршрутизация идемпотентна (безопасна к ретраям): повтор исходного → та же маска;
повтор маски → тот же исходный; конфликт → 409; нет ПД → без ложного конфликта.
Перегрузка → 429 с Retry-After. Таймаут запроса — 10 секунд; ретраи до 2 (3 попытки).

## 3. Работа в интерфейсе

### Быстрая демонстрация без настройки

1. Откройте сайт: первым появится экран **«Демонстрация»** с заполненным синтетическим примером.
2. Нажмите **«Проверить»**: сервис маскирует текст и сразу проверяет его точное восстановление.
3. Сравните исходный текст с блоками **«После маскирования»** и **«После восстановления»**; выше показаны число фрагментов и измеренное время полного цикла, включая HTTP-запросы.
4. В списке **«Пример»** сравните публичную личность, клиента с тем же именем и смешанный контекст; поле также принимает собственный текст, а **«Вернуть пример»** возвращает исходный синтетический пример.
5. Ключ не нужен: используется существующий профиль `autocheck`; LLM в этой проверке не вызывается, а дополнительные возможности доступны через **«Инструменты»**.

### Расширенная проверка

Откройте **«Инструменты» → «Расширенная проверка»**. Защищённые профили требуют свой API-ключ приложения; это не ключ внешней модели.

1. Выберите приложение (потребителя) в правом верхнем углу. Видна версия политики.
2. Введите текст с персональными данными в поле ввода.
3. Нажмите **«Обработать текст»** — появится замаскированный запрос (справа), затем ответ демонстрационного провайдера (слева).
4. **«Демаскировать запрос»** — точное восстановление исходного запроса.
5. **«Демаскировать ответ»** — восстановление токенов внутри ответа провайдера.
6. Карточка **«Результат проверки»** — найденные фрагменты, категории, время, статус, политика, request id.
7. Для потребителя с отключённым egress показывается «Отправка модели отключена для этого приложения».
8. Статус **«Демонстрационный провайдер — без внешнего вызова»** — ответ stub, не реальная модель.
9. **«Очистить»** — сброс вида браузера (серверный контекст сохраняется до TTL).


### 5.3. Комбинационное правило (combination_demo)

```
PIN: 4321
```
→ PIN сохраняется (нет связанной карты в записи).

```
карта 4276189074144957, PIN: 4321
```
→ PIN маскируется (карта в той же записи).

```
карта 4276189074144957
PIN: 4321
```
→ PIN сохраняется (карта и PIN на разных строках — разные записи).

### 5.4. Повтор после потери ответа

Отправьте один и тот же исходный текст дважды с одним `payload_id` — вернётся та же маска. Отправьте замаскированный текст с тем же `payload_id` — вернётся исходный.

## 6. Правила и reload

Правила задаются в `configs/consumers.yaml` (per-consumer: `detect_types`, `default_action`, `allow_unmask`, `allow_llm_egress`, `combination_rules`). Новый тип данных добавляется в `configs/detectors.yaml` через config-driven regex detector (без правки ядра). Изменение не требует правки ядра. После изменения перезапустите сервис — новая версия политики появится в `/config` и в интерфейсе.

## 7. Логи и метрики

- `/metrics` — счётчики и гистограммы latency (mask/unmask/chat/process), без ПД в метках.
- Логи — структурированные, только allowlist-поля, без исходных ПД и ключей.
